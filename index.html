AURA: Unified Multimodal Framework for Conversational Music Editing

AURA：對話式音樂編輯的統一多模態框架

Quoc-Huy Trinh, Minh-Van Nguyen, Debesh Jha
arXiv:2609.14344 · cs.SD · 投稿submitted 2026-09-13
abspdfhtmlcited by
為什麼挑這篇：AURA 把整段對話歷史、圖片與參考音訊濃縮成概念符記，注入凍結的 MusicGen-medium 骨幹進行音樂編輯，跨域（分佈外）新增與移除任務的 FAD 分別從 3.84 降到 0.84、從 3.55 降到 0.72，約有 4.6 到 4.9 倍的改善，且三輪連續編輯下 SI-SDR 仍維持在 +5.1 dB，遠優於基準 Instruct-MusicGen 的 -19.3 dB。Why this one: AURA compresses full dialogue history, images, and reference audio into concept tokens injected into a frozen MusicGen-medium backbone, cutting out-of-domain addition and removal FAD from 3.84 to 0.84 and from 3.55 to 0.72 (roughly 4.6-4.9x), while holding SI-SDR at +5.1 dB after three sequential edits versus -19.3 dB for the Instruct-MusicGen baseline.

動機Motivation

音樂製作是反覆修改的過程：使用者聽過一次生成結果後，常常想「先把鼓拿掉」，再「加一段貝斯」，再「把貝斯換成更暖的音色」。這些指令彼此有依賴關係，後一句的真正意思要靠前幾輪對話才能確定。

AURA 的作者指出，現有的指令式音樂編輯系統——AUDIT、InstructME、M2UGen、Instruct-MusicGen、LeVo 2——全部把每次指令當成獨立事件處理，不會記得使用者前幾輪說過什麼。這在單次編輯的展示裡看不出問題，但在真實的多輪製作流程中，系統必須讓每次新編輯都與先前已經定案的內容保持一致，否則使用者等於每次都要重新描述整首歌目前的樣子。

Music production is an iterative back-and-forth: after hearing one generated result, a user often wants to 'remove the drums,' then 'add a bass line,' then 'make that bass warmer' -- instructions whose meaning depends on what was said in earlier turns.

The authors observe that existing instruction-guided music editors (AUDIT, InstructME, M2UGen, Instruct-MusicGen, LeVo 2) all treat each request independently and retain no memory of prior turns. This is invisible in single-edit demos, but in real multi-turn production workflows the system must keep every new edit consistent with what was already finalized, or the user ends up re-describing the entire track state every time.

背景與相關研究Introduction & Prior Work

背景音樂生成本身站在 MusicLM、MusicGen、Stable Audio 這類文字轉音樂骨幹之上，這些模型擅長從文字描述生成新音樂，但不是為了「編輯」既有音軌設計的。指令式編輯這條線上，AUDIT 用潛在擴散模型做音訊編輯，InstructME 專門處理音樂的加/減/混音指令，Instruct-MusicGen 則是把指令調校加進 MusicGen 做文字轉音樂編輯——這三者是 AURA 論文實驗裡拿來比較的主要對手，論文簡稱其中最強的基準為 Instruct-MG。

這些系統的共同點，也是 AURA 點名的差異所在：它們都是「單輪」系統，每次呼叫只看當下這一句指令與當下的音訊，不會讀對話歷史。AURA 的做法是用 Qwen2.5-Omni 這個多模態語言模型讀完整段對話、圖片與參考音訊，萃取出九個「概念符記」，再靠這些符記去控制一個凍結的 MusicGen-medium 解碼器。換句話說，AURA 不是重新設計一個更會生成音樂的模型，而是在既有的文字轉音樂骨幹外面，加一層「理解多輪意圖」的介面——這是它與 AUDIT、InstructME、Instruct-MusicGen 最根本的差異。

The music-generation backbone here builds on MusicLM/MusicGen/Stable Audio-style text-to-music models, which are good at generating new music from text but were not designed for editing an existing track. On the instruction-editing side, AUDIT performs audio editing via latent diffusion, InstructME handles music add/remove/remix instructions specifically, and Instruct-MusicGen adds instruction-tuning on top of MusicGen for text-guided editing -- these three are the main opponents AURA compares against experimentally, with the strongest baseline referred to in the paper as Instruct-MG.

What these systems share, and where AURA marks its difference, is that they are all single-turn: each call only sees the current instruction and current audio, with no memory of dialogue history. AURA instead uses the multimodal LLM Qwen2.5-Omni to read the full conversation, images, and reference audio, distilling nine 'concept tokens' that then steer a frozen MusicGen-medium decoder. In other words, AURA is not a better music generator -- it is a multi-turn-intent-understanding layer bolted onto an existing text-to-music backbone, which is its core distinction from AUDIT, InstructME, and Instruct-MusicGen.

方法Method

系統輸入是圖片（可選）、完整對話歷史與參考音訊，輸出是編輯後的音軌。第一步由 Qwen2.5-Omni 的 Thinker 模組讀進三種輸入，同時輸出自然語言回覆與 9 個特殊 ⟨EDIT_CONCEPT⟩ 符記的隱藏狀態，這些符記因為在注意力機制裡看得到所有前面的模態與對話輪次，所以能濃縮出「要做什麼操作、對哪個樂器、要什麼音色屬性、以及對話上的限制」。第二步是兩條獨立的投影路徑：概念投影器把符記狀態轉成 MusicGen 維度的「要改什麼」向量，音訊投影器把凍結 EnCodec 編碼器抽出的參考音訊逐畫面轉成「要保留什麼」向量。

第三步是解碼：骨幹是凍結的 MusicGen-medium（19 億參數凍結，AURA 只訓練 9100 萬參數）。作者設計了兩個新模組——雙向特徵對齊模組（BiFAM），用共享的位置對齊查詢把參考音訊揉進解碼器每一層，並用初始化為恆等映射的 FiLM 調變，確保沒有破壞預訓練權重的行為；以及概念交叉注意力，讓解碼器輸出去查詢概念符記，用 rank-64 的 LoRA 轉接器實作、所有層共用同一組概念向量。推論時用 classifier-free guidance（guidance scale 2.0），把概念向量替換成全零來做無條件的那一次前向。

The system takes an optional image, full dialogue history, and reference audio as input and outputs an edited track. First, Qwen2.5-Omni's Thinker module reads all three inputs and produces both a natural-language reply and hidden states for 9 special ⟨EDIT_CONCEPT⟩ tokens; because these tokens attend to every prior modality and dialogue turn, they compactly encode the operation, target instrument, desired attributes, and conversational constraints. Second, two separate projection paths follow: a concept projector maps the token states into a 'what to change' vector in MusicGen's space, while an audio projector turns the frozen EnCodec encoding of the reference audio into a frame-aligned 'what to preserve' vector.

Third is decoding, on a frozen MusicGen-medium backbone (1.9B parameters frozen, with only 91M trained). The authors add two new modules: a Bidirectional Feature-Alignment Module (BiFAM) that fuses the reference audio into every decoder layer via a shared position-aligned query, modulated by a FiLM transform initialized as an identity mapping so pretrained behavior is not disturbed at the start; and a concept cross-attention block, where the decoder output queries the concept tokens through rank-64 LoRA adapters shared across all layers. At inference, classifier-free guidance (scale 2.0) runs the unconditional pass by zeroing out the concept vector.

限制Limitations

作者自己點名的限制只有一個，但講得很具體：分離（stem extraction）這項任務上，一個生成式解碼器打不過專門做音源分離的模型——論文的抽取任務數據也印證這點，同域（Slakh2100）SI-SDR 只有 -7.62 dB、跨域（MoisesDB）也只有 +2.67 dB，是三個任務裡數字最差的一項，遠不如新增與移除任務動輒兩位數正 dB 的表現。作者自己提出的解法是把 AURA 接上一個獨立的分離前端模型，而不是硬要生成式解碼器同時做生成又做分離。

The authors name exactly one limitation, and it is specific: for the stem-extraction task, a generative decoder cannot match a dedicated source-separation model. The paper's own extraction numbers back this up -- in-domain (Slakh2100) SI-SDR is only -7.62 dB and out-of-domain (MoisesDB) only +2.67 dB, the weakest of the three tasks compared with the double-digit positive dB seen on addition and removal. The authors' own proposed fix is to pair AURA with a separate dedicated separation front-end rather than asking one generative decoder to both generate and separate.

討論Discussion

多輪實驗（移除鼓 → 加貝斯 → 加吉他）最能看出對話歷史的實際作用：到第三輪，AURA 的 SI-SDR 仍有 +5.1 dB，Instruct-MG 已經掉到 -19.3 dB；作者另外做了一個對照組，只給系統看「最後一句指令」而不給完整對話，結果 SI-SDR 掉到 -5.2 dB、SSIM 從 0.54 掉到 0.49——證明真正帶來效果的是「記得前幾輪」這件事，不是模型本身比較強而已。消融實驗也支持這個判斷：把概念符記換成完整文字的隱藏狀態，新增任務的 FAD 從 0.84 惡化到 13.32，顯示濃縮成 9 個符記這個設計本身就是關鍵，而不是換一個更大的語言模型就能達到一樣效果。

The multi-turn experiment (remove drums → add bass → add guitar) shows the value of dialogue history most clearly: by turn three, AURA still holds SI-SDR at +5.1 dB while Instruct-MG has collapsed to -19.3 dB. A control condition that shows the system only the final instruction, without full history, drops SI-SDR to -5.2 dB and SSIM from 0.54 to 0.49, confirming that remembering prior turns -- not just a stronger backbone -- drives the gain. The ablation supports this too: swapping concept tokens for full-text hidden states worsens addition FAD from 0.84 to 13.32, showing that distilling intent into 9 tokens is itself the key design choice, not simply using a bigger language model.

Building a Dataset for Music Sample Identification

建構一個音樂取樣識別資料集

R. Oguz Araz, Xavier Lizarraga, Xavier Serra, Dmitry Bogdanov
arXiv:2609.15465 · cs.SD · 投稿submitted 2026-09-14
abspdfhtmlcited by
為什麼挑這篇：作者從 WhoSampled 社群資料庫挖出 9.2 萬筆取樣標註、涵蓋 13 萬首曲目，建成比既有取樣識別基準（Sample100、SamplePairs，各自只有約 100 筆標註）大了近三個數量級的 WhoSampled130k 資料集；更關鍵的是，他們發現直接把邊隨機切成訓練/驗證/測試集（80/10/10）會讓測試集裡 54% 的節點其實已經出現在訓練或驗證集中，於是改用連通元件切分，只是為了處理佔全部節點一半以上的「巨型元件」，必須先移除 2.5 萬個多重取樣父節點，代價是捨棄 23% 的節點。Why this one: The authors mined 92k sampling annotations covering 130k tracks from the WhoSampled community database, building WhoSampled130k -- almost three orders of magnitude larger than existing sample-identification benchmarks (Sample100 and SamplePairs, each around 100 annotations); more importantly, they found that naively splitting edges 80/10/10 into train/val/test leaves 54% of test nodes already appearing in train or validation, so they switched to splitting by connected components, which required removing 25k multi-parent nodes to break up a single mega-component holding over half of all nodes, at the cost of discarding 23% of nodes.

動機Motivation

取樣識別（sample identification）要做的事是找出一首新歌裡用了哪首舊歌的哪個片段——這是版權查核與音樂考古都會用到的檢索任務，但這個領域長期缺基礎設施。作者指出既有的兩個基準 Sample100 與 SamplePairs 都只有大約 100 筆標註，而且 Sample100 還只收嘻哈曲風，測試集小到無法支撐現代深度學習模型的訓練與可靠評估。在此之前，沒有任何公開、大規模的取樣識別訓練或評估資料。

Sample identification means finding which earlier track, and which segment of it, was reused inside a new recording -- a retrieval task useful for both copyright checks and music archaeology, but one the field has long lacked infrastructure for. The authors point out that the two existing benchmarks, Sample100 and SamplePairs, each carry only around 100 annotations, and Sample100 is further restricted to hip-hop tracks -- far too small to train or reliably evaluate a modern deep-learning model. Before this work, no large-scale public training or evaluation dataset existed for the task.

背景與相關研究Introduction & Prior Work

先前兩個基準都是從 WhoSampled 手動挑選出來的小樣本：Sample100（Van Balen et al., 2013）只收錄約 100 筆嘻哈曲風的取樣標註，SamplePairs（Riou et al., 2026）規模相近但不限曲風，兩者都小到只能拿來做評估，無法拿來訓練模型。同時也有幾篇近期方法論文——Cheston et al.（2025）用多損失訓練加合成資料做自動識別、Bhattacharjee et al.（2025）用自監督圖神經網路、Riou et al.（2026）用多軌對比學習——但它們都是在演算法端下功夫，共同的瓶頸是可用的訓練資料太少。

這篇論文的差異在於它不是提出新演算法，而是直接解決「資料從哪裡來」這個更根本的瓶頸：同樣挖 WhoSampled，但規模上直接跳兩個數量級到 9.2 萬筆標註、13 萬首曲目，並且是第一個處理切分洩漏問題的取樣識別資料集——先前的基準因為規模太小，從未真正遇到「同一首歌同時出現在訓練集與測試集」這種問題。

Both prior benchmarks were small samples hand-picked from WhoSampled: Sample100 (Van Balen et al., 2013) contains about 100 hip-hop-only sampling annotations, and SamplePairs (Riou et al., 2026) is similar in size but not genre-restricted -- both too small to train on, useful only for evaluation. Several recent method papers also work in this space: Cheston et al. (2025) use multi-loss training with synthetic data for automatic identification, Bhattacharjee et al. (2025) use a self-supervised graph neural network, and Riou et al. (2026) use multi-track contrastive learning -- but all of them attack the algorithm side, sharing the same bottleneck of too little training data.

This paper's contribution is different: rather than a new algorithm, it fixes the more fundamental bottleneck of where the data comes from. It still mines WhoSampled, but jumps two orders of magnitude to 92k annotations over 130k tracks, and is the first sample-identification dataset to confront split leakage -- a problem the earlier, much smaller benchmarks never really encountered because a track appearing in both train and test sets was rare at their scale.

方法Method

作者從 WhoSampled 下載約 17 萬首曲目（約占整個資料庫 20%）的取樣中繼資料與音檔，轉成一個以曲目為節點、取樣關係為邊的有向圖，先移除 6 個簡單環讓它變成有向無環圖，再用 NetworkX 找出連通元件，並依結構分成孤立配對、孤立鏈、樹、複雜元件四類。分析發現有一個「巨型元件」含 9.4 萬個節點，超過全部節點的一半，是由 Amen break 和 Lyn Collins〈Think〉這類被大量取樣的曲目所共同衍生出來的後代匯聚而成。

直接照邊切分（80/10/10）會讓 100 次重複實驗平均有 54% 的測試節點與訓練/驗證集重疊（標準差僅 0.002 個百分點，顯示這不是偶然）。作者改成照連通元件切分，因為元件天生節點互斥、每條邊完整落在單一元件內。為了解決巨型元件佔比過半的問題，他們移除「多重取樣父節點」（有超過一個上游來源的節點）把巨型元件打散成 9000 個小元件，代價是捨棄 23% 的節點（2.5 萬個多重父節點加 1.3 萬個因此變孤立的節點）；最終切分是把 Sample100、SamplePairs 裡分別 71%、50% 的比對節點放進測試集，37 個複雜元件放進訓練集，其餘依 90/5/5 隨機分配，得到訓練 114721 首、驗證 6374 首、測試 10444 首曲目。

The authors downloaded sampling metadata and audio for about 170k tracks (roughly 20% of the whole WhoSampled database), turned it into a directed graph with tracks as nodes and sampling relations as edges, removed 6 simple cycles to make it acyclic, and then used NetworkX to find connected components, classified into isolated pairs, isolated chains, trees, and complex components. The analysis found one mega-component of 94k nodes -- over half of all nodes -- formed from the shared descendants of heavily sampled tracks like the Amen break and Lyn Collins' 'Think.'

Splitting edges directly 80/10/10 leaves 54% of test nodes overlapping train/validation on average across 100 repeated trials (standard deviation just 0.002 percentage points, so this is not a fluke). The authors instead split by connected component, since components are node-disjoint and every edge sits entirely inside one component. To fix the mega-component's over-half share, they remove 'multi-parent' nodes (nodes with more than one upstream source), breaking it into 9k smaller components at the cost of discarding 23% of nodes (25k multi-parent nodes plus 13k nodes left isolated as a result); the final split places 71% and 50% of Sample100's and SamplePairs' matched nodes respectively into the test set, assigns 37 complex components to training, and randomly splits the rest 90/5/5, yielding 114,721 training, 6,374 validation, and 10,444 test tracks.

限制Limitations

作者列了好幾項具體限制，而不是空泛帶過：WhoSampled 的標註本身不完整，大部分標註缺少「被取樣的是哪一段」，樂器角色也從未標出，時間戳精度只到 1 秒且不涵蓋每次出現；由於標註不完整，圖只能建在「曲目層級」而非「取樣片段層級」，所以嚴格說這是一張取樣關係圖而不是取樣片段圖。

另外，切分過程本身可能製造「假性斷開的元件」，造成訓練集與測試集之間仍有殘留的洩漏——尤其是那 198 個從被移除的多重父節點衍生出來的元件，雖然作者認為因為在原圖裡路徑長度至少為二、實際影響應該很小，但無法完全排除。用 YouTube ID 去比對 Sample100 與 SamplePairs 的節點也可能有比對失敗的偽陰性。

The authors list several concrete limitations rather than a vague disclaimer: WhoSampled annotations are incomplete -- most lack which part was actually sampled, musical roles are never given, and 1-second-resolution timestamps don't cover every occurrence; because of this, the graph could only be built at the track level rather than the sample-appearance level, so strictly it is a sampling graph, not a sample-appearance graph.

The splitting process can also create falsely disconnected components, leaving some residual train/test leakage -- particularly the 198 components descending from removed multi-parent nodes, which the authors expect to be small since they sit at least two edges away in the raw graph, but cannot fully rule out. Matching nodes to Sample100 and SamplePairs via YouTube IDs may also produce false-negative matches.

討論Discussion

作者把自己的資料集定位成「有意識到洩漏風險，而不是完全無洩漏」——連通元件切分在圖的觀測範圍內確實不會洩漏，但巨型元件的存在逼他們做了一個明確的取捨：修剪掉 23% 的節點換取乾淨的切分邊界。他們把「保留巨型元件又不洩漏」列為未來工作，沒有假裝這是已解決的問題。

整篇論文沒有做任何識別模型的訓練或評估，純粹是資料集與切分方法論文，這點在讀這篇分析時要記住——它衡量的是資料基礎設施的品質，不是某個模型的準確率。

The authors frame their contribution as 'leakage-aware rather than leakage-free' -- component-based splitting is provably leakage-free with respect to the observed graph, but the mega-component forced an explicit trade-off: trimming 23% of nodes to get clean split boundaries. They list retaining the mega-component without leakage as future work, without pretending it is already solved.

The paper trains and evaluates no identification model at all -- it is purely a dataset-and-splitting-methodology paper, worth keeping in mind when reading this analysis: it measures data-infrastructure quality, not any model's accuracy.

ScorePrompts: Natural-Language Exploration of Symbolic Music Scores through Analysis

ScorePrompts：透過分析達成樂譜的自然語言探索

Emmanouil Karystinaios, Gerhard Widmer

為什麼挑這篇：ScorePrompts 讓使用者上傳 MusicXML 樂譜，先跑一整套既有的符號音樂 MIR 模型（AnalysisGNN 等）分析出和聲、調性、終止式、樂句與段落邊界、織度與音符角色，再把這些結構化結果餵給一個受基模約束的語言模型去生成自然語言解說與回答提問，而不是讓語言模型直接看 MusicXML 猜結構。論文沒有提供任何量化指標、基準比較或消融實驗，作者自己也承認還沒有做過使用者研究，所以這篇的貢獻是系統設計本身，不是「效果比誰好」的實證證據。Why this one: ScorePrompts lets users upload a MusicXML score, runs it through an existing stack of symbolic-music MIR models (AnalysisGNN, etc.) to extract harmony, tonality, cadences, phrase/section boundaries, texture, and note-level roles, and only then feeds these structured results to a schema-constrained language model that generates explanations and answers questions -- rather than letting the LLM guess structure directly from MusicXML. The paper reports no quantitative metrics, baseline comparisons, or ablations, and the authors themselves acknowledge no user study has been done, so the contribution here is the system design itself, not empirical proof that it outperforms anything.

動機Motivation

樂譜用圖形記譜法編碼音高、同時性、聲部、拍子與大尺度結構，這些資訊一旦被攤平成 token 序列或原始 MusicXML 標記，很容易就流失掉。作者認為單靠自然語言也不夠：使用者應該能夠回頭檢查「這段解釋是根據樂譜的哪個區域、哪一層分析結果」，而不是把語言模型的說法當黑盒子全盤接受。ScorePrompts 的核心設計哲學是「先分析、再生成」——用符號音樂 MIR 模型先建出一份帶類型、對齊到樂譜位置的結構化表示，語言模型全程只能看得到這份表示，分析過程本身則一路保持可檢視。

Graphical notation encodes pitch, simultaneity, voice, meter, and large-scale organization in ways that get lost once a score is flattened into a token sequence or raw MusicXML markup. The authors argue natural language alone is not enough either: a user should be able to check which score region and which analytical layer actually support a given explanation, rather than taking an LLM's account at face value. ScorePrompts' core design philosophy is 'analyze before generating' -- symbolic-music MIR models first build a typed, score-aligned structured representation, the language model only ever sees that representation, and the analysis stays inspectable throughout.

背景與相關研究Introduction & Prior Work

先前把樂譜與自然語言連起來的系統走的是不同路線。C@merata（Sutcliffe et al., 2015）把英文描述直接對應到 MusicXML 段落，是語言到樂譜的直接映射；ChatMusician（Yuan et al., 2024）把 ABC 記譜法本身當成語言模型可以直接生成的序列；Dai et al.（2026）的「樂譜理解基準」則直接測試通用語言模型能不能看懂完整樂譜，結果顯示多層次的音樂推理對通用語言模型仍然很難。這三者的共通點是要嘛依賴語言模型直接讀懂記譜細節，要嘛提供一個測出「讀不懂」的基準，但都沒有在語言模型前面放一層專門的符號音樂分析。

ScorePrompts 的差異正是這一層：它假設樂譜已經是機器可讀的 MusicXML，在語言生成之前先跑一套固定、可檢視的 MIR 分析堆疊（和聲、調性、終止式、樂句與段落等），語言模型的工作被限縮成「把已經算好的結構化欄位轉述成解釋」，而不是自己去理解記譜。這一點也把它與同期的 MuseAgent-1（Zhao et al., 2026，整合光學音樂辨識與演奏音訊的多模態代理推理）區分開——ScorePrompts 刻意不做多模態推理，只處理已經是符號格式的樂譜。

Prior systems linking scores to natural language took different routes. C@merata (Sutcliffe et al., 2015) maps English descriptions directly onto MusicXML passages -- a direct language-to-score mapping; ChatMusician (Yuan et al., 2024) treats ABC notation itself as a sequence an LLM can generate directly; and Dai et al.'s (2026) Musical Score Understanding Benchmark tests whether general-purpose LLMs can comprehend complete scores at all, finding that 'multi-level musical reasoning remains difficult for general language models.' What these three share is either relying on the LLM to read notation details directly, or a benchmark that measures its failure to do so -- none place a dedicated symbolic-analysis layer in front of the language model.

ScorePrompts' difference is exactly that layer: assuming the score is already machine-readable MusicXML, it runs a fixed, inspectable MIR analysis stack (harmony, tonality, cadence, phrase/section, etc.) before any language generation, reducing the LLM's job to rephrasing already-computed structured fields rather than understanding notation itself. This also separates it from the contemporaneous MuseAgent-1 (Zhao et al., 2026), which integrates optical music recognition and performance-audio analysis through agentic multimodal reasoning -- ScorePrompts deliberately skips multimodal reasoning and only handles scores already in symbolic form.

方法Method

系統分四個階段。第一階段由 Partitura 讀入 MusicXML 並對齊事件，AnalysisGNN 估計和聲、調性、終止式、樂句、段落與音符角色等屬性，再用確定性後處理重建羅馬數字並在拍子與小節層級彙整；另外用 AlgoMus 風格的織度描述子與透過 music21 取得的 jSymbolic 風格特徵補充上下文。整份樂譜被表示成一串重疊的小節區塊，每塊帶欄位定義、分類代碼與局部分析結果，並全部透過小節參照與音符 ID 對齊，建立一個全域證據索引保存所有已解碼區塊與整體走向。

第二階段是受基模約束的語言生成：分析出的欄位先被轉成標準化的「小節事實」，配合整段樂曲層級的走向，語言模型才依此生成三種技術深度遞增的描述；生成內容裡引用的位置都會對照證據索引檢查，格式不對就重試或退回確定性摘要，語言模型本身沒有做任何音樂領域的微調——傳給它的是類型化的 MIR 表示，而不是樂譜標記本身。第三階段是確定性的問答路由：系統解析問題裡提到的小節範圍與和聲、終止式、曲式相關詞彙，直接從證據索引挑出對應欄位回答，不需要再呼叫語言模型，回答內容會把「結論」與「引用的小節、支持的分析層、但書與結構化參照」分開列出，讓不同分析層之間的分歧看得見。第四階段用 Verovio 把原始記譜連同重建的羅馬數字標籤一起呈現，點選音符可以看到它的識別碼、音高、時間、和聲與結構標籤及信心值。

The system has four stages. Stage 1: Partitura loads the MusicXML and aligns events, AnalysisGNN estimates harmony, tonality, cadence, phrase, section, and note-role attributes, and deterministic post-processing reconstructs Roman numerals and aggregates them at beat and measure level; AlgoMus-style texture descriptors and jSymbolic-style features via music21 add further context. The whole score becomes a sequence of overlapping measure chunks, each carrying field definitions, categorical codes, and local analysis results, all aligned via measure references and note IDs, with a global evidence index retaining every decoded chunk and overall trajectory.

Stage 2 is schema-constrained language generation: analyzed fields are first turned into canonicalized 'measure facts' combined with piece-level trajectories, and only then does the language model generate three descriptions of increasing technical depth; any location it cites is checked against the evidence index, with malformed output triggering a retry or a deterministic fallback summary, and the LLM itself receives no music-specific fine-tuning -- what it sees is the typed MIR representation, not the score markup. Stage 3 is deterministic question routing: the system parses measure ranges and harmony/cadence/form terms in a question and pulls the matching fields straight from the evidence index without another LLM call, separating a concise takeaway from the cited measures, supporting layers, caveats, and structured references so disagreements between analytical levels stay visible. Stage 4 renders the original notation via Verovio alongside reconstructed Roman-numeral labels; clicking a note reveals its identifier, pitch, timing, harmonic/structural labels, and confidence values.

限制Limitations

作者列出的限制相當坦白。第一，系統可以追溯到樂譜衍生欄位與有效的小節或音符識別碼，但作者明講「不保證每句生成出來的話在語意上真的對應那些欄位，也不保證上游 MIR 模型的預測在音樂學上是對的」——換句話說，可追溯不等於正確。第二，目前的原型只針對機器可讀的西方調性樂譜，直接繼承了底層 MIR 元件的曲目與標註假設，換一種記譜傳統或非調性音樂大概率失效。第三，系統不能編輯記譜，而且作者自己承認還沒有做過使用者研究——這意味著論文裡展示的所有互動範例都只是設計示範，沒有第三方或音樂家驗證過品質。

The authors' limitations are notably candid. First, results can be traced to score-derived fields and valid measure or note identifiers, but the authors state directly that they 'do not establish that each generated sentence is semantically linked to those fields, nor that the upstream predictions are musicologically correct' -- traceability is not the same as correctness. Second, the current prototype targets only machine-readable Western tonal scores and inherits the repertory and annotation assumptions of its underlying MIR components, so it likely fails on other notation traditions or non-tonal music. Third, the system cannot edit notation, and the authors themselves admit no user study has been conducted -- meaning every interaction example shown in the paper is a design demonstration, not something validated by a third party or a musician.

討論Discussion

作者把貢獻定位成「讓分析結果本身成為主要證據層，而不是要語言模型取代符號分析」，並強調把分析、語言生成、檢索與呈現分成獨立模組，是為了讓每個部分都能被單獨檢驗與評估。他們列出的下一步包括：檢查生成語句與證據之間是否真的語意相符、把逐區塊分析彙整成完整樂曲層級的描述、加入 RAG 式檢索來支援問答、以及找音樂家做任務型評估。

整篇論文沒有一個數字可以拿來跟其他系統比較——這點在寫這篇分析時必須說清楚，不能因為系統設計精巧就暗示它「效果好」，因為論文根本沒有測過效果。

The authors position their contribution as making analysis outputs the primary evidence layer rather than asking a language model to replace symbolic analysis, and emphasize that separating analysis, language generation, retrieval, and rendering into independent modules lets each be evaluated on its own. Their listed next steps include checking whether generated sentences are actually semantically linked to the evidence, aggregating chunk-level analysis into full-score descriptions, adding RAG-style retrieval for Q&A, and running task-based evaluation with musicians.

Not a single number in the paper can be compared against another system -- worth stating plainly here, since a well-designed system is not the same claim as an effective one, and this paper never measured effectiveness.
